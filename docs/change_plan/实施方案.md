# 基于 DeepSeek Harness 的自动化实验室 MVP 实施方案

本文是一份面向 Codex 的架构参考。目标是在不重建 Agent 框架、通用工作流平台和完整实验云工作台的前提下，用可解析的真实实验资料、全局知识服务、版本化 Protocol、确定性 Runtime 和全局设备服务完成空间 ATAC 复杂空转，并形成论文与融资演示所需的可复现实验证据。任务顺序、依赖和每轮验收由 [开发编排计划](开发编排计划.md) 统一管理。

## 1. 决策摘要

第一版只交付一个可运行闭环：

```text
PDF / DOCX 实验资料
        ↓
全局知识服务解析、分类、检索和确认
        ↓
复杂空间 ATAC Protocol
        ↓
Agent 生成本次实验计划
        ↓
确定性校验器拒绝缺参数、越界参数和无设备能力的计划
        ↓
人工批准一次受限执行计划
        ↓
确定性运行时执行模拟设备和必要人工确认节点
        ↓
设备回执、人工确认、异常和 Agent 决策写入会话日志
        ↓
生成可复核的空转实验报告
```

第一版不建设完整实验云平台，不实现九个独立 Agent，不开发 Workflow Library、通用 Skill 编译器、企业级知识管理前端、视觉模型、自动知识演进或跨进程调度器。MVP 必须实现最小的全局 Knowledge Service、PDF/DOCX 解析、可追溯事实确认和混合检索，因为 Agent 需要从真实实验资料形成 Protocol 和计划。

计划采用“完整复杂 Protocol + 全量模拟设备能力 + 明确人工门禁”的软件 MVP 定义。复杂 Protocol 的全部步骤都进入计划和审计链；所有应由设备执行的步骤都必须通过模拟 Device Provider 自动执行，不允许以人工点击“完成”替代设备回执。模拟 Provider 是真实 Device Service 的正式实现之一，而不是页面演示桩。本文可以据此证明 Agent 驱动自动实验平台的软件闭环可行，但不得表述为真实硬件已经联调完成。

## 2. 现有方案的主要问题与优化结论

### 2.1 建设顺序过重

原方案在真实硬件前安排了完整领域数据库、Experiment IR、三层 Skill 系统、Skill Matcher、Skill Expansion、Capability Registry、Device Registry、Compiler、Runtime、Planner、Verifier、前端和多阶段 API。该顺序会使团队在验证核心假设前先承担平台化成本。

优化后的顺序是：先锁定资料、Protocol、知识、LabOperation 和设备接口，再并行完成确定性模拟骨架与 PDF/DOCX 导入，随后把确认知识编译为 Protocol 并接入 Planner Agent。真实设备接口到位后，在同一 Device Service 下新增 Provider 并进入硬件在环测试。

### 2.2 Harness Skill 不是可执行实验动作

`@deepseek-ai/dsh-skill` 提供 Agent 指令目录，不负责参数绑定、设备命令、状态迁移或物理执行。第一版保留 Harness Skill，用于向 Planner Agent 提供 Protocol 解析和工具使用说明；可执行动作统一命名为 `LabOperation`，由类型、校验规则和设备能力绑定定义。不得把 `SKILL.md` 当作设备程序或运行时节点。

### 2.3 `dsh-workflow` 不作为物理实验运行时

`@deepseek-ai/dsh-workflow` 执行模型编写的子 Agent 编排脚本，当前实现没有运行日志恢复和进程重启续跑。实验执行采用新增的确定性 `LabRunService`。Harness 的 `ctx.jobs` 只承载单进程内后台执行和状态通知；实验事实写入 Session 事件。进程异常退出后，未完成运行进入 `RECOVERY_REQUIRED`，模拟模式可从事件重建后由用户批准恢复；未来真实设备模式还必须核对设备和样本状态。

### 2.4 前端和多 Agent 不是首个证据

前期 HTML 中“资料提交—方案生成—实验监控—结果反馈—实验优化”的五段式流程继续作为产品蓝图，但九个数字员工、资源甘特图、Workflow Library 和完整配置中心不进入 MVP。前端作为 Consumer 随 Service 纵向迭代：文档收件箱、知识确认、设备视图、实验控制台、Agent 规划和证据面板分别在对应后端能力可用后接入，不建设独立前端项目，也不在浏览器维护第二份业务状态。

### 2.5 论文论点必须可检验

“复杂实验完成，因此简单实验一定能完成”只能作为复杂度支配假设，不能直接作为论文结论。论文需要证明所选复杂实验覆盖长步骤链、多种设备、时间窗口、分支、人工操作、QC 和异常恢复等复杂度维度，并通过参数变化、步骤删减、设备替换或故障注入说明系统不是单协议硬编码。
### 2.6 全局知识、SOP、Skill 与设备分工

Knowledge Service 和 Device Service 在 Host 层全局注册，但查询和操作必须携带组织、团队、项目、实验及权限范围。知识按类型、实验、设备、版本和确认状态路由检索；权限和有效状态使用硬过滤，知识类别使用可回退的软路由，避免错误分类降低召回率。

PDF/DOCX 是不可变来源，确认后的结构化事实编译为 ProtocolDefinition。Harness Skill 只指导 Agent 检索知识、加载 Protocol、查询能力、生成和修复计划；固定代码能力保存为 LabOperation，并由 LabRunService 通过全局 Device Service 执行。Harness Skill 和 `dsh-workflow` 均不能直接调用硬件驱动。


## 3. 实验资料审计结论

当前 CSV 在标题行之后只有 43 条实验记录，序号从 15 跳到 17，后续步骤 `4-1` 又依赖缺失的 `3-6`。`3-5` 的步骤名称为 `noListClick`，显然不是可执行实验语义。这两项必须在编码前由实验人员修正。

43 条记录中，27 条标记为 `DOC_CONFIRM`，16 条标记为 `OBSERVATION_REQUIRED`；24 条要求现场观察，19 条不要求。43 条记录全部处于“待确认”，且“人工/全自动/半自动”列全部为空。

多数字段写有“立即”“文档未给最大等待”或“需确认恢复规则”。这些内容不能由 Agent 猜测，也不能用默认值静默填充。未确认的硬时间窗、QC 阈值、试剂等待条件和恢复策略必须成为 `UNRESOLVED` 约束，校验器在真实执行模式下拒绝相关节点。

### 3.1 设计阶段必须登记的问题

| 编号 | 问题 | 负责角色 | 关闭条件 |
| --- | --- | --- | --- |
| P0-01 | 缺失 `3-6`，记录数与“44 步”不一致 | 实验负责人 | 补齐步骤或修正全部后继依赖 |
| P0-02 | `3-5` 名称为 `noListClick` | 实验负责人 | 给出正式步骤名、输入、输出和完成条件 |
| P0-03 | 自动化属性为空 | 软件负责人 + 实验负责人 | 根据步骤语义先标记 `DEVICE`、`MANUAL` 或 `APPROVAL`，并保留待实验人员复核状态 |
| P0-04 | 真实设备和通讯接口未知 | 软件负责人 | 定义与厂商无关的 Device Service 和模拟能力配置；真实协议作为后续 Provider 输入 |
| P0-05 | 多个“立即”和等待上限未量化 | 实验负责人 | 真实执行节点具有明确超时或明确人工裁决要求 |
| P0-06 | QC 与文档参数存在冲突 | 实验负责人 | 每项冲突形成带版本和署名的裁决记录 |
| P0-07 | 空转边界未定义 | 实验负责人 + 安全负责人 | 明确是否装空耗材、是否加水、是否允许加热/旋转、是否执行机械运动 |

这些问题不阻塞软件原型开发。无法从表格确定的值以 `ASSUMED_FOR_SIMULATION` 保存，并在运行报告中列出；不得静默伪装为已确认 SOP。P0-01 和 P0-02 必须在 Protocol 导入时形成显式缺口或临时修复映射，不能让依赖图悄悄断裂。

## 4. MVP 范围

### 4.1 必须交付

- 一份版本化的空间 ATAC `ProtocolDefinition`，覆盖修正后的完整复杂步骤链、三个后续分支、输入输出、依赖、参数、时间窗、QC、执行模式和来源。
- 一个 Planner Agent，由 DeepSeek Harness 驱动，将用户实验请求和协议定义转换为本次 `ExperimentPlan`。
- 一个全局 Knowledge Service，支持知识作用域、类型、版本、确认状态、来源引用、冲突和混合检索。
- 一个 PDF/DOCX 解析 Provider，保存原始文件哈希、Parser 版本、段落、表格、页码、坐标和 OCR 来源，并将失败保留为可查询状态。
- 一个本地知识 Provider，使用 SQLite 保存权威元数据和事实，使用 FTS 与可配置 Embedding Provider 建立可重建索引。
- 一个基于现有 Web Client 的最小实验工作台，分块交付文档上传、知识确认、计划批准、设备状态、实验运行和证据查看。
- 一个确定性校验器，至少校验结构、依赖环、缺参数、单位、参数范围、时间窗、样本/容器引用、设备能力、人工门禁和未确认字段。
- 一个确定性运行时，按依赖关系推进节点，支持开始、暂停、人工确认、失败安全停止、取消和状态查询。
- 一组按 Capability 配置的模拟 Device Provider，覆盖表格中 PCR、温控、离心、液滴、显微成像、计数、片段分析和液体操作等设备角色，并支持正常、忙碌、延迟、离线、超时、命令拒绝和错误回执。
- 一个自动执行闭环：完整 Protocol 被 Agent 规划和校验，所有 `DEVICE` 节点由模拟设备自动执行，确属人工职责的步骤才进入人工确认，系统自动汇总运行结果。
- 一个 Provider 兼容性套件，保证未来真实 Provider 可以复用同一命令、状态和回执语义，而不修改 Agent、Protocol 和 Runtime。
- 全链路审计和正常、离线、超时、非法参数、人工拒绝、进程中断后的安全恢复检查。

### 4.2 明确不做

- 不训练 Planner 或领域小模型。
- 不建设企业级通用 RAG、独立向量数据库集群、通用 ORM 或知识管理前端；MVP 只实现实验资料需要的全局知识接口、本地 Provider 和可替换检索实现。
- 不建设 Workflow Library、Workflow Template Library 或 Composite Skill 演进系统。
- 不把 43/44 步协议逻辑写进 Runtime 的条件分支。
- 不实现多实验并发、跨实验资源优化、跨进程自动恢复或生产级排队。
- 不实现九个独立 Agent、完整定制工作台、权限中心、知识库管理页和设备管理页。
- 第一版不引入视觉模型；模拟显微和成像能力通过结构化状态与产物回执表达，图像判定作为后续独立能力验证。
- 不实现真实厂商 Provider，直到获得设备型号、协议或 SDK。
- 不宣称完成真实硬件联调或处理真实生物样本；第一阶段结论覆盖 Agent 驱动自动实验平台的软件可行性。

## 5. MVP 成功标准

1. 修正后的复杂 Protocol 可被同一个通用 Schema 完整表达，Runtime 中没有 `if experimentType === "space-atac"` 一类协议专用分支。
2. Planner 生成的计划必须经过确定性校验和人工批准；校验失败的计划无法启动。
3. 表格中所有 `DEVICE` 节点均由模拟 Provider 完成预检、命令提交、运行状态变化、完成回执和停止验证，不以固定计时动画代替状态协议。
4. 完整空转运行从开始到报告结束，不需要开发者手工修改运行状态或数据库。
5. 每个自动节点保存命令摘要、幂等键、时间和回执；每个人工节点保存操作者、选择和时间。
6. 注入离线、超时、非法参数和人工拒绝后，系统不会向下一物理步骤继续。
7. 参数变化、步骤或分支变化、同能力模拟设备替换无需修改 Runtime；Provider 兼容性测试证明未来真实设备只需实现 Device Service。
8. 一次空转运行可以从 Session 日志重建计划、状态时间线和最终报告。

## 6. 技术栈
9. PDF/DOCX 可以生成带页码和区块来源的知识；冲突和未确认值不会被静默编译为真实执行 Protocol。
10. 全局设备可以被不同实验发现，但只有持有有效租约的运行能够提交设备命令。

技术栈以仓库当前实现为准。Node.js Host 负责服务和运行时；Docling 通过可配置 Python 模块 Provider 接入，不建立第二套 Agent 或业务 API 服务：

| 层 | 采用技术 | MVP 用法 |
| --- | --- | --- |
| 运行时 | Node.js `^22.19 || >=24`、ESM、TypeScript strict | 实验插件、设备接口和状态机 |
| 构建 | pnpm workspace、TypeScript 6、tsx、tsdown | 延续现有包和构建流程 |
| 插件框架 | Cordis | 服务注册、插件组合、生命周期和 Provider 替换 |
| Agent | `core/agent`、`core/agent-loop`、DeepSeek Provider | 规划、解释错误、生成报告 |
| 工具 | `core/tools` | 向 Agent 暴露最小实验工具 |
| 审计 | `core/session` + Session persistence | 记录模型可见事实和实验事件 |
| 后台执行 | `jobs/jobs` + `jobs-local` | 单进程模拟空转任务，不承诺自动跨进程续跑 |
| 人工交互 | `user-questions`、`user-approval` | 计划批准；后台人工节点使用确认工具 |
| Agent 指令 | `skill/skill` + `skill-filesystem` | 加载 Planner 说明，不执行物理动作 |
| Web | React 18 插件式 Web Client、API Gateway | 复用会话和工具 UI |
| 校验 | TypeScript + Zod 或仓库既有 schema 机制 | 校验跨边界输入 |
| 测试 | Vitest、真实 Cordis composition、keyless snapshot | 单元、装配和模型输出测试 |
| 文档解析 | Python + Docling SDK | PDF/DOCX、表格、版面和 OCR 来源解析 |
| 知识存储 | Provider 自有 SQLite + 不可变文件目录 | 文档、版本、事实、冲突、FTS 和索引版本 |
| 知识检索 | 结构化过滤 + FTS + 可配置 Embedding Provider | 分域召回、跨域回退、重排和引用 |

模拟设备使用与真实 Provider 相同的类型接口，以配置文件定义能力、运行时长、状态序列、回执和故障。未来设备通讯优先使用厂商 SDK/HTTP 或 gRPC、标准串口/TCP、受支持的命令行程序；不得通过模拟鼠标点击承担安全关键控制。凭证、地址和安全参数通过 Cordis 配置提供。

## 8. 最小领域模型

### 8.1 ProtocolDefinition

`ProtocolDefinition` 是经人工确认、版本化的实验定义，不是 Agent 每次自由生成的 Workflow。

```text
interface ProtocolDefinition {
  protocolId: string
  version: string
  title: string
  sourceDigest: string
  steps: ProtocolStep[]
}

interface ProtocolStep {
  id: string
  title: string
  dependsOn: string[]
  executionMode: "DEVICE" | "MANUAL" | "APPROVAL" | "SIMULATED"
  operation: string
  capability?: string
  inputs: ValueRef[]
  outputs: ValueRef[]
  parameters: Record<string, Quantity | string | boolean>
  preconditions: Rule[]
  completion: Rule[]
  qc?: Rule[]
  timeoutMs?: number
  latestStartOffsetMs?: number
  onFailure: "STOP" | "WAIT_OPERATOR" | "RETRY_ONCE"
  provenance: Provenance
  confirmation: "CONFIRMED" | "ASSUMED_FOR_SIMULATION" | "UNRESOLVED"
}
```

单位是值的一部分，不允许用无单位裸数字表达温度、体积、转速、离心力、时间和浓度。`sourceDigest`、`provenance` 和确认信息保证复现并防止协议被静默改写。

### 8.2 ExperimentPlan

Planner 只能选择已有 Protocol 步骤、绑定已注册 Operation、提供参数和选择允许的分支，不得创造未知设备命令。

```text
interface ExperimentPlan {
  planId: string
  protocolId: string
  protocolVersion: string
  mode: "SIMULATED_EMPTY_RUN" | "PHYSICAL_EMPTY_RUN"
  selectedSteps: PlannedStep[]
  assumptions: string[]
  unresolved: string[]
}
```

`SIMULATED_EMPTY_RUN` 允许使用显式的 `ASSUMED_FOR_SIMULATION` 值，但 `unresolved` 非空或能力未绑定时仍不得启动。`PHYSICAL_EMPTY_RUN` 只接受 `CONFIRMED` 参数和真实 Provider，当前阶段保留该模式的校验入口但不声称完成。

### 8.3 LabOperation 与 DeviceCapability

`LabOperation` 是确定性动作，例如 `thermal_cycle.run_program`、`centrifuge.run`、`droplet_generator.run_program` 和 `operator.confirm`。Agent 只调用计划和运行工具；`LabRunService` 是唯一能向 `LabDeviceService.execute()` 提交命令的组件。

### 8.4 LabRun 状态

```text
DRAFT → VALIDATED → AWAITING_APPROVAL → APPROVED → RUNNING
RUNNING ↔ WAITING_OPERATOR
RUNNING → COMPLETED
任意执行态 → PAUSED_SAFE | FAILED_SAFE | CANCELLED | RECOVERY_REQUIRED
```

`FAILED_SAFE` 只表示系统停止继续发命令，不表示设备必然已物理停止。Provider 必须分别报告超时、停止请求、停止结果和设备最终状态。

## 9. 模块划分

目录名是实施目标，Codex 在 TASK-LAB-000 中核对仓库聚合配置和命名规则后才能创建。

### 9.1 `packages/experimental/lab-protocol`

Protocol、Plan、Operation、Rule 和 Quantity 类型与校验；CSV 导入结果校验；依赖排序；参数、单位、确认状态和执行模式检查。它不负责 Agent Prompt、设备通讯、运行调度、数据库和 UI。

### 9.2 `packages/experimental/lab-device`

`LabDeviceService` Service Definition、全局 Device/Capability Registry、动态状态、租约、命令和回执类型、幂等键、查询、停止和健康检查语义。设备全局可发现，但只有持有有效租约的 LabRunService 可以执行；厂商字段只存在于 Provider 内。

### 9.3 `packages/experimental/lab-device-mock`

`MockHardwareProvider` 按 `LabDeviceService` 的正式接口返回可配置数据，覆盖 PCR、温控、离心、液滴、显微成像、计数、片段分析和液体操作。Mock 数据必须形成与未来真实 Provider 同构的结构化模拟回执，包括命令标识、设备状态、开始与结束时间、产物引用、错误码和证据来源。它提供确定性故障注入，支持 `NORMAL`、`BUSY`、`DELAY`、`OFFLINE`、`TIMEOUT`、`REJECTED` 和 `FAILED`。

`Mock` 是 Provider 的实现方式，`SIMULATED` 是回执和报告的证据标签。两者同时保留：前者约定接口与测试替身，后者防止论文、演示或审计把 Mock 结果解释为物理设备结果。

### 9.4 `packages/experimental/lab-device-<model>`

真实设备 Provider 的预留位置，不在当前软件 MVP 中创建空包。设备型号和协议明确后实现配置验证、连接、预检、命令转换、回执规范化、超时、停止、断线和错误码映射。

### 9.5 `packages/experimental/lab-runtime`

`LabRunService`、状态投影、依赖推进、设备租约、人工等待、安全停止和实验 Session 事件。MVP 只允许一个活动运行，但设备命令仍携带运行标识和租约；不建设通用 Scheduler、Queue 或跨实验资源优化器。

### 9.6 `packages/experimental/tool-lab`

第一版只暴露：

```text
lab_protocol_inspect
lab_plan_validate
lab_run_start
lab_run_status
lab_run_confirm
lab_run_stop
lab_run_report
```

`lab_run_start` 只接受已校验和批准的计划引用，禁止接受任意脚本或任意设备命令。

### 9.7 `packages/experimental/lab-mvp`

在现有 base/web 组合上插入知识、Protocol、实验插件、Planner Skill 和模拟 Provider。第一版不修改官方默认 profile，以显式 opt-in bundle 或 overlay 启动；未来通过配置替换知识或真实设备 Provider。


### 9.8 `packages/experimental/lab-knowledge`

全局 Knowledge Service Definition，定义文档、版本、解析运行、区块、事实、冲突、引用、作用域、知识类型、确认和检索接口。

### 9.9 `packages/experimental/lab-knowledge-local`

本地 Knowledge Provider，负责不可变原始文件、Docling、SQLite、FTS、Embedding Provider 接口、索引版本、混合检索和重建。数据库和索引由 Provider 持有，Agent 和其他消费者不能直接访问。

### 9.10 `packages/experimental/tool-lab-knowledge`

Agent Consumer，提供文档导入状态、知识检索、冲突查询和事实确认工具；返回值必须携带权限范围、文档版本、页码、区块和原文引用。

### 9.11 `packages/experimental/lab-mvp-web`

Web Consumer，按纵向切片提供文档收件箱、知识确认、全局设备视图、实验控制台、Agent 规划和证据面板。所有状态来自 Service、Tool 结果或 Session 事件投影；页面不得直接连接设备或使用定时动画伪造完成。

## 11. 模拟硬件与真实接入预留

### 11.1 模拟硬件不是演示动画

每个模拟设备从配置读取 `deviceId`、Capabilities、允许参数范围、状态迁移、运行时长、并发限制和故障场景。运行时必须通过 `LabDeviceService` 调用模拟设备并等待状态与回执，不得按页面定时器直接把节点标记为成功。

模拟设备至少覆盖表格出现的设备类别。相同 Capability 可以配置两个模拟设备，用于验证 Agent/Resolver 能在设备忙碌或离线时选择替代设备；不同 Capability 之间通过 ExperimentPlan 的依赖关系协同。

### 11.2 Device Provider 必须实现

```text
describeCapabilities()
healthCheck()
execute(command, idempotencyKey, signal)
getStatus(operationId)
stop(operationId, reason)
```

重复幂等键不得触发第二次物理动作；无法证明幂等时必须拒绝并进入人工核对。

### 11.3 当前与后续证明边界

- 软件 MVP 证明 Agent 能把复杂 Protocol 转为可验证计划，并通过统一设备接口完成自动调度、执行、异常处理和审计。
- 模拟空转证明控制软件可行，不证明厂商协议兼容性、物理动作精度、真实生物结果或实验室安全性。
- 真实硬件协议到位后，必须增加硬件在环验证，才能形成“真实自动化实验室”结论。
- 论文、路演和报告分别统计 `SIMULATED`、`MANUAL` 和未来的 `PHYSICAL` 证据，不混合成功率。

## 12. 开发阶段与工期

详细任务、依赖图、状态和 Codex 每轮范围以 [开发编排计划](开发编排计划.md) 为准。本节只保留架构级里程碑。加入真实文档解析、全局知识服务和混合检索后，软件 MVP 预计 22–30 个工作日；硬件协议缺失不阻塞模拟阶段。

### 阶段 0：Protocol 与模拟假设锁定，2–3 个工作日

- 修正 `3-5`、缺失 `3-6` 和依赖。
- 从表格推导每步执行模式和所需 Capability，保留待确认标记。
- 把未给出的等待上限、QC 冲突和恢复策略登记为假设或缺口。
- 定义模拟设备配置、标准命令、状态和回执。
- 输出 Harness 复用矩阵和最终包清单。

退出条件：完整依赖图可以加载；所有设备步骤映射到 Capability；每个未知值都有可追溯状态。

### 阶段 1：确定性数字闭环，5–7 个工作日

- 建立最小包骨架、ProtocolDefinition 和校验器。
- 实现模拟 Provider、故障注入、状态机、人工等待和报告工具。
- 完成 Ground Truth Plan 的确定性模拟空转。
- 同步交付三节点运行的最小实验控制台，验证页面状态来自 Runtime 和事件投影。

退出条件：不使用 Agent 也能执行已批准 Ground Truth Plan；非法计划和故障按预期失败。

### 阶段 2：文档解析、知识沉淀与知识前端，5–8 个工作日

- 导入 PDF/DOCX，保存原文哈希、Document IR、页码和区块来源。
- 建立知识范围、类型、事实确认、冲突、FTS、Embedding 接口和混合检索。
- 交付文档收件箱和知识确认视图，从确认事实编译 ProtocolDefinition，并与 Ground Truth 比较。

退出条件：至少一份真实 DOCX 和 PDF 可以形成带来源的 Protocol；上传、解析失败和事实确认过程可观察；冲突和未确认值不会进入物理执行。

### 阶段 3：Agent 驱动复杂模拟空转，5–7 个工作日

- 实现 Planner Skill、结构化 ExperimentPlan 和修复循环。
- 由 Agent 查询 Capability、选择设备、提交计划并启动运行。
- 覆盖完整复杂 Protocol、三个分支、人工门禁和自动报告。
- 同步交付 Agent 规划视图，展示知识引用、计划修复和 Validator 结果，不展示内部推理文本。

退出条件：开发者不改代码和状态即可连续完成三次复杂模拟空转，且所有设备节点来自 Provider 回执。

### 阶段 4：故障、自适应与泛化验证，3–5 个工作日

- 注入忙碌、离线、超时、QC 失败和人工拒绝。
- 验证同 Capability 设备替换、受约束重试和失败安全停止。
- 运行参数、步骤删减和分支变化三类 Protocol 变体。
- 同步交付全局设备视图和证据面板的首个切片，所有指标从事件与检索记录读取。

退出条件：故障后没有错误推进；设备替换和 Protocol 变体无需修改 Runtime。

### 阶段 5：论文与演示交付，3–5 个工作日

- 完成 LLM-only、LLM + Validator、Full System 消融。
- 生成结构化指标、失败样本、复现实验说明和演示录屏。
- 明确标注当前结论来自模拟硬件空转。

退出条件：论文数字能追溯到事件日志和运行标识，模拟证据没有被表述成物理实验结果。

### 后续阶段：真实 Provider 与硬件在环

设备文档到位后实现一个或多个真实 Provider，运行 Provider 兼容性测试、安全测试和完整物理空转。该阶段不改 Agent、Protocol Schema、Runtime 或工具语义；若必须修改，应记录接口抽象缺陷并重新验证模拟与真实 Provider。

### Protocol Ground Truth

将 CSV 转为带来源状态的 ProtocolDefinition。完整步骤、依赖和三个分支可加载；缺失依赖、环、无单位参数和非法停止点被拒绝；可配置模拟假设必须显式出现在报告中。

### Global Device Service Definition

根据表格设备角色定义同时满足模拟与未来真实设备的最小接口。验收包括完整能力接缝、注册卸载对称、branded id、Provider 兼容性测试、README 和 JSDoc。

### Mock Hardware Provider

实现覆盖当前设备角色的 `MockHardwareProvider`，按照正式 Device Service 返回结构化模拟回执，并支持正常、忙碌、延迟、离线、超时、拒绝和失败场景。每个故障通过真实 Service 路径测试，取消等待子任务退出。

### Deterministic Lab Runtime

实现单运行状态机、依赖推进、人工等待、安全停止和 Session 事件。只有 `VALIDATED + APPROVED` 的计划可启动；失败不推进后继；遗留运行投影为 `RECOVERY_REQUIRED`；Runtime 不调用 LLM。

### Agent Tools 与 Planner Skill

Agent 无直接设备命令工具；结构化输出在工具边界校验；模型可见输入全部来自日志；真实 composition snapshot 覆盖完整对话。

### Agent-Driven Complex Empty Run

运行完整复杂 Protocol 的 Agent 驱动模拟硬件闭环，覆盖正常、人工拒绝、非法参数、离线和超时。除明确人工节点外，所有设备步骤必须从模拟 Provider 获得回执。

### Generalization and Paper Evaluation

运行参数、步骤/分支和设备能力变体，完成故障、消融和指标导出。统计从结构化事件读取，实验配置和运行标识可复现，失败样本不删除。

### Real Device Provider，后续

设备协议到位后实现真实 Provider。参数上限、幂等、预检、回执、超时、停止和断线通过硬件在环验证；凭证和地址不进入日志。

### Physical Empty Run，后续

用真实 Provider 替换模拟 Provider，ProtocolDefinition、ExperimentPlan Schema、Runtime 和 Agent Tools 不修改；完成三次连续现场空转。

## 15. 测试策略

### 15.1 单元测试

- Schema：额外字段、未知 Operation、单位缺失、NaN、负时间、越界参数和不完整回执。
- 图：缺失依赖、环、不可达节点、非法分支和重复输出。
- 状态机：允许和禁止迁移、重复确认、重复命令和终止竞态。
- 事件折叠：相同日志得到相同状态，损坏日志拒绝加载。

### 15.2 真实组合与 Snapshot

通过测试专用 `cordis.yml` 从 Loader 启动实际 bundle，验证 Agent、Tool、Session persistence、Jobs、Mock Hardware Provider 和 Runtime。Keyless snapshot 覆盖计划、校验拒绝、批准、后台运行、人工节点和设备故障报告。

### 15.3 Provider 兼容性与 Mock 真实性

用同一组测试约束所有 Device Provider：预检、状态序列、规范化回执、重复幂等键、非法参数、断线、超时、停止和取消。Mock Hardware Provider 还必须证明结果由接口输入、能力配置和故障场景共同决定，而不是由 Protocol 步骤名称硬编码；其返回值必须通过与真实 Provider 相同的回执解析和状态推进路径。真实 Provider 到位后复用该套测试并增加厂商硬件安全测试。

## 16. 论文实验设计

### 16.1 研究问题

- RQ1：Agent 能否把复杂实验请求转换为满足确定性约束的计划？
- RQ2：Agent 能否通过统一设备接口自主推进复杂模拟空转，并根据设备状态和异常采取受约束行动？
- RQ3：Validator、人工批准和 Runtime 分别减少哪些错误？
- RQ4：参数、步骤结构或 Provider 改变后是否无需修改 Runtime？

### 16.2 指标

| 维度 | 指标 | 来源 |
| --- | --- | --- |
| 规划 | 首次通过率、修复轮数、非法操作召回率 | plan/validation 事件 |
| 执行 | 节点完成率、运行完成率、设备成功率 | node/device/run 事件 |
| 人工 | 介入次数、介入时长、拒绝次数 | operator 事件 |
| 安全 | 越界拦截率、故障后错误推进次数 | validator 与状态机事件 |
| 效率 | 计划耗时、空转墙钟时间、等待时间 | 事件时间戳 |
| 泛化 | Protocol 变体通过率、Provider 替换代码改动量 | 运行与 Git diff |
| 可追溯 | 有来源的计划项、有关联回执的真实节点比例 | provenance 与 receipt |

### 16.3 对照与复杂度证据

至少比较 LLM-only、LLM + deterministic validator、Full System 三组。空间 ATAC 的复杂度量化为步骤数、最长依赖链、分支数、设备种类、人工节点数、时间窗数、QC 节点数和故障类型数。完成复杂实验后，从同一 Protocol 派生步骤删减和参数简化变体验证简单子流程。

## 17. 风险与降级

| 风险 | 降级策略 |
| --- | --- |
| 设备无开放协议 | 不阻塞软件 MVP；登记真实 Provider 输入清单并保持模拟证据标签 |
| Protocol 未确认 | 使用显式标记的模拟假设运行，并在报告中列出全部未确认项 |
| 工具超时或会话关闭 | Runtime 作为 Job；事件持久化；中断后人工恢复 |
| Job 不能跨进程恢复 | 投影为 `RECOVERY_REQUIRED`，不自动续发命令 |
| Planner 不稳定 | 固定 Protocol 版本、缩小输出字段、强制 Validator |
| 人工节点过多 | 如实报告自动化覆盖率，按介入时长选择下一设备 |
| 单协议硬编码质疑 | 增加变体、Provider 替换和故障注入 |
| 模拟与真实混淆 | 每个节点和指标强制带 evidence mode |
