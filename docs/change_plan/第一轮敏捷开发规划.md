# 自动化实验平台第一轮敏捷开发规划

> 日期：2026-08-26
>
> 状态：第一轮基础闭环已完成，当前进入可操作原型收口。`pdf-knowledge-parser` 负责资料录入、PDF/SOP、索引召回和 Knowledge 工作区，`lab-harness-native-workspace` 负责 Harness 原生侧栏、项目多 Session、Agent 对话、计划确认和执行反馈；两线通过版本化 Knowledge Consumer 接口并行施工，联合验收通过后第一轮才完成。
>
> 适用范围：基于 DeepSeek Harness 建设通用自动化实验最小原型

## 1. 文档定位

本文定义自动化实验平台第一轮开发的产品目标、系统分层、模块责任、核心接口、技术路线、敏捷增量和验收标准，是第一轮最小原型的执行依据。

[实施方案](实施方案.md)继续描述长期产品与技术方向，[开发编排计划](开发编排计划.md)继续描述完整路线图。本文只收敛第一轮原型；与两份长期文档的第一开发块冲突时，第一轮以本文为准，长期范围仍由原文档负责。

当前施工细节分别由 [PDF 与知识路径 OpenSpec](../../openspec/changes/pdf-knowledge-parser/proposal.md) 和 [Harness 原生工作区 OpenSpec](../../openspec/changes/lab-harness-native-workspace/proposal.md) 维护。本文只定义它们在第一轮中的位置、依赖和联合完成条件；实时任务状态以 OpenSpec 为准。

现有 HTML 只提供业务流程或交互参考，不是最终页面、运行状态或执行节点的来源。空间 ATAC CSV、PDF 和鼠脑空间转录组流程均为测试资料，系统不得通过硬编码资料内容通过验收。

## 2. 第一轮产品目标

第一轮交付一个可运行的通用闭环：用户录入实验资料，表达实验需求，Agent 检索知识并生成实验计划与实验 Skill 草案，用户确认后由确定性运行时执行已批准步骤，系统验证结果、记录证据并形成反馈。

```text
资料录入
  → 文档解析、SOP 草案与缺口
  → 人工补全、确认并发布知识
  → 在项目中创建 Harness Session
  → 用户通过原生对话表达实验需求
  → Agent 按项目范围检索已发布知识
  → 生成实验计划与 Skill 草案
  → 确定性校验
  → 人工确认
  → Skill 解析与步骤执行
  → 设备、API、脚本或人工操作
  → 结果验证
  → 报告、反馈与实验上下文沉淀
```

首轮不是单个 2–5 日 Sprint，而是一条由基础闭环、两条并行收口线和联合验收组成的 MVP 交付列车。每个施工切片保持 2–5 个工作日并提供独立演示，最终联合验收完成端到端闭环。

## 3. 已确认的产品与安全规则

1. 测试资料只用于验证通用能力，不成为运行时代码中的固定实验流程。
2. Agent 生成的计划和步骤必须经过确定性校验与人工确认后才能执行。
3. 每个计划步骤必须引用一个已批准的实验 Skill 修订；Skill 再展开为一个或多个受控操作。
4. Agent 可以生成声明式 Skill 草案，包括步骤说明、输入输出、参数、前置条件、完成条件、工具绑定和已安装资源引用。
5. Agent 生成的新脚本只能保存为候选资产，首轮不得自动执行；硬件脚本、API 客户端和设备操作代码来自已安装 Skill 或 Provider。
6. Skill 生命周期固定为 `DRAFT → VALIDATED → HUMAN_APPROVED → ACTIVE → RETIRED`。运行实例锁定 Skill 修订，新修订不能改变已开始的实验。
7. Runtime 只执行已激活 Skill，并通过受控 Service 或 Operation Executor 调用能力，不执行模型输出的任意代码。
8. 设备命令只能由 Runtime 通过 Device Service 提交。Agent 可以查询能力和提出计划，不能直接控制设备。
9. 模型可见输入、计划、确认、步骤结果和反馈必须写入 Session 事件，能够从日志重建。
10. 实验缓存只保存当前实验的可重建投影、Skill 快照、检索引用和中间产物引用，不成为第二个事实来源。
11. 首轮所有业务包保持 opt-in 和 experimental，不修改官方默认 profile。
12. Agent 接入复用 DeepSeek Harness 现有的 `ctx.agents`、Agent preset、LLM adapter、`ctx.tools`、`ctx.skills`、`ctx.approval`、Session、`ctx.storage` 和 `ctx.subprocess`；不新增实验专用 Agent 配置、独立审批总线、并行会话协议或第二套 Agent loop。

## 4. 方案选择

### 4.1 采用：能力接缝与纵向增量

知识、实验 Skill、设备和运行分别建立 Service Definition、Provider 与 Consumer。第一轮按资料录入、规划确认、执行验证的纵向链路逐步接通，每个增量同时包含最小服务、失败语义、工具或 UI 和真实组合测试。

这种方案允许后续替换文档解析器、RAG Provider、设备 Provider 和运行 Provider，同时避免一次性建设大量没有用户入口的基础模块。

### 4.2 不采用：先完成所有基础层再统一集成

横向建设全部数据库、RAG、Skill、设备和 Runtime 后再接 Agent 与 UI，会把反馈推迟到开发末期，也无法及时发现接口只适合单一消费者的问题。

### 4.3 不采用：由 Agent 直接生成并运行脚本

动态代码直接运行无法可靠控制设备权限、幂等、停止、审计和版本。首轮只执行已安装且已批准的操作实现，动态脚本进入候选资产流程。

### 4.4 Agent 接入：复用 Harness 的配置与组合方式

Agent 创建、恢复和模型选择沿用 Harness 现有流程：调用方通过 `ctx.agents.create()` / `ctx.agents.resume()` 提供 `agentOptions`，在 `setup(agentCtx)` 中挂载 Agent scope；Agent preset 通过 `ctx.agentPresets.mount()` 提供稳定的工具、提示和 Skill 组合。实验系统只补充实验领域服务和工具，不在 Runtime 内部重新创建 Agent。

实验工具作为普通 `ctx.tools.register()` Consumer 加入既有 Agent scope，阶段可见性使用 preset 组合或 `ctx.tools.restrict()` 控制；实验操作指导继续进入 `ctx.skills`，实验 Skill 生命周期仍由 `LabSkillService` 管理。计划和步骤确认使用 `ctx.approval`，审计与模型上下文使用 Session，缓存使用 `ctx.storage`，解析器和已安装资源使用 `ctx.subprocess` 与沙箱。

这条复用规则意味着 `lab-mvp` 不提供 `LabAgentService`、不持有 provider/model/api-key 配置，也不修改 Harness `agent-loop`。第一轮 Agent 组合测试必须证明：既有 preset 创建的 Agent 能发现实验工具，工具能调用实验服务，计划/确认/执行状态能进入既有 Session。

```text
Web / Agent Conversation
        │
        ├── Knowledge Tools ── Knowledge Service ── Local RAG Provider
        │                                              ├── Immutable Files
        │                                              ├── Parser / Chunker
        │                                              ├── SQLite + FTS
        │                                              └── Embedding Index
        │
        ├── Planning Tools ── Planner Coordinator
        │                         ├── Protocol Validator
        │                         ├── Lab Skill Service
        │                         └── Device Capability Query
        │
        └── Run Tools ── Lab Run Service ── Operation Executor Registry
                                  ├── Device Executor ── Device Service ── Mock Provider
                                  ├── Human / Approval Executor
                                  ├── Installed Script Executor
                                  └── Installed API Executor

Session Events ── 审计、模型上下文、确认与运行时间线
Storage / SQLite ── 业务数据、RAG 索引与可重建投影
Artifact Files ── 原始文件、解析产物、脚本候选与结果文件
```

| 层 | 责任 | 不负责 |

| Agent 协作层 | 意图解析、知识检索、计划草拟、Skill 草拟、解释校验错误 | 绕过 Validator、批准计划、修改运行状态 |

## 8. 核心服务和基础类型设计

仓库采用 Cordis Service 与 Provider 接口，不新增通用 `BaseService`、`BaseRepository` 或多层抽象继承。共享类型放在领域包，行为通过窄接口和组合扩展。

### 8.1 KnowledgeService

核心操作：`importDocument`、`getImportStatus`、`listImportStatuses`、`getDocument`、`search`、`listConflicts`、`confirmFact` 和 `rebuildIndex`。

所有检索结果必须包含文档版本、页码或区块、原文引用、确认状态和检索得分。权限与有效状态先做硬过滤，关键词和向量结果统一重排。

### 8.2 LabSkillService

核心操作：`createDraft`、`validateDraft`、`approveDraft`、`activateRevision`、`resolveRevision`、`snapshotForRun` 和 `retireRevision`。

`LabSkillDefinition`至少包含名称、版本、目标、适用条件、输入输出、参数约束、操作列表、完成条件、失败策略、来源引用和资源引用。每个 `PlanStep` 必须锁定一个 `SkillRevisionId`。

Harness `ctx.skills`继续承担模型指令发现与加载。`LabSkillService`承担实验动作定义和生命周期；Provider 可以把已激活实验 Skill 的说明投影为 Harness Skill，但不得改变 `ctx.skills` 的既有语义。

### 8.3 OperationExecutor

Runtime 维护按判别标签注册的 Operation Executor。第一轮实现 `device`、`human` 和 `approval`；`script` 与 `api`定义资源引用和校验字段，只执行已安装实现。

每个执行器都接收运行 ID、步骤 ID、Skill 修订、标准化参数、幂等键和取消信号，并返回结构化 Observation 或明确错误。执行器不能直接推进后继步骤。

### 8.4 LabDeviceService

核心操作：`describeCapabilities`、`listDevices`、`healthCheck`、`reserve`、`execute`、`getStatus`、`stop` 和 `release`。

同一设备不能被两个有效租约同时占用；重复幂等键不能触发第二次动作。停止结果与设备最终状态分别记录，通信失败不能显示为执行成功。

### 8.5 LabRunService

Runtime 核心操作：`createExperiment`、`approvePlan`、`startRun`、`confirmStep`、`stopRun`、`getRun` 和 `buildReport`；`propose`、`validatePlan`、`approvePlan` 与 `rejectPlan` 的计划审核状态由 `LabPlanningService` 负责，Runtime 只接受已确认且可锁定的计划输入。

Runtime 加载已批准 Plan 与 Skill 快照，生成本次 ExecutionGraph。它不调用 LLM，不读取原始文档，也不允许调用方提交任意设备命令。

## 9. Agent 工具设计

工具按阶段和 Agent Preset 暴露，避免把全部 schema 同时放进每次模型请求。

工具实现必须复用 Harness 的工具协议和 Agent scope：工具由 `ctx.tools.register()` 注册，使用既有参数/输出 schema、取消信号、超时、幂等和执行审计；不创建实验专用 tool registry。工具所属的 Agent、模型、preset 和 provider 由 Harness 配置决定，实验工具不自行选择模型或注入 API key。

### 9.1 知识阶段

- `lab_knowledge_import`：登记资料并启动解析。
- `lab_knowledge_status`：查询解析、索引和失败状态。
- `lab_knowledge_search`：按实验上下文检索并返回引用。
- `lab_knowledge_conflicts`：列出冲突和未确认事实。
- `lab_knowledge_confirm`：提交具名人工确认。

### 9.2 规划阶段

- `lab_experiment_create`：登记用户目标和实验上下文。
- `lab_plan_context`：检索带引用的知识上下文、冲突和只读设备事实。
- `lab_plan_devices`：只读查询设备与 Capability。
- `lab_plan_propose`：提交结构化计划和声明式 Skill 草案，执行确定性校验。
- `lab_skill_validate`、`lab_skill_approve`、`lab_skill_activate`：分阶段审核并激活 Skill 修订。
- `lab_plan_approve`、`lab_plan_reject`：人工确认或拒绝计划，并保留修订血缘。

### 9.3 执行阶段

- `lab_run_start`：只接受已批准计划引用。
- `lab_run_status`：读取运行、步骤和待确认事项。
- `lab_run_confirm`：提交人工步骤或结果确认。
- `lab_run_stop`：请求安全停止。
- `lab_run_report`：生成带引用、回执和证据模式的报告。

## 10. RAG 与数据库方案

### 10.1 权威数据与派生数据

- 首轮本地 Provider 将原始字节、文档版本、元数据、区块和索引保存在 `lab-knowledge-local` 自有 SQLite；文件内容 SHA-256 作为文档和版本身份，重复导入保持幂等。
- 生产级不可变文件区和大产物内容寻址存储仍是后续替换点，不影响当前 Provider 接口。
- FTS 与向量索引是可删除并重建的派生数据，索引失败不改变已确认事实。
- 模型可见事实、计划决策、人工确认和执行时间线写入 Session 事件。
- 当前实验缓存使用 `ctx.storage` 保存可重建投影、检索引用、Skill 快照和中间产物引用。

### 10.2 首轮 RAG

首轮使用结构化过滤、SQLite FTS5、可配置 Embedding Adapter 和统一重排。小规模向量保存在 SQLite，由 Provider 在进程内完成相似度计算；数据量或并发需要独立索引时，再替换为 PostgreSQL + pgvector 或专用向量 Provider。

DeepSeek Harness 当前没有通用实验 RAG 或 Embedding Service。第一轮在 Knowledge Provider 内使用窄 `EmbeddingAdapter`，获得第二个独立消费者后再决定是否提升为公共能力接缝。

### 10.3 文档解析

Docling 通过可配置 Python 模块由 `ctx.subprocess`与沙箱调用，不建立第二套 Agent 或业务 API。解析结果规范化为 DocumentBlock、表格、页码、坐标、标题路径和 OCR 来源。

密码保护、文件损坏、解析器不可用、无文本层和不支持格式必须形成可查询失败状态，不添加静默文本提取兜底。

## 11. 关键领域对象

| 对象 | 责任 |
| --- | --- |
| `KnowledgeDocument` / `DocumentVersion` | 原始资料身份、版本、哈希和解析状态 |
| `DocumentBlock` / `KnowledgeFact` / `Citation` | 结构化内容、确认状态和来源 |
| `ExperimentRequest` | 用户目标、样本、约束、预期产物和缺失信息 |
| `ProtocolDefinition` | 经确认的实验规则、步骤候选和来源版本 |
| `ExperimentPlan` / `PlanStep` | 本次实验选择的步骤、依赖、参数和 Skill 修订 |
| `LabSkillDraft` / `SkillRevision` | 声明式实验能力、操作绑定、资源和生命周期 |
| `LabOperation` | `device`、`human`、`approval`、`script` 或 `api` 操作 |
| `ExecutionGraph` | 本次运行从已批准计划和 Skill 快照生成的执行图 |
| `ExperimentRun` / `StepExecution` | 运行状态、尝试、时间、输入输出和错误 |
| `Observation` / `ValidationResult` | 设备回执、人工结果、规则判断和证据 |
| `FeedbackRecord` | 用户反馈、偏差、改进候选和来源运行 |

所有跨资源 ID 使用 branded ID。温度、时间、体积、浓度和转速等量值携带单位；未知值、假设值与已确认值使用显式状态，不能用默认值掩盖。

## 12. Skill 生成、执行与沉淀

### 12.1 生成

Planner 检索知识后优先复用已激活 Skill。没有匹配项时，它生成声明式 Skill 草案，并附上知识引用、假设、未解决项和建议操作绑定。

### 12.2 校验与批准

Validator 检查字段、依赖、参数、单位、引用、操作执行器、资源存在性、Capability、完成条件和失败策略。校验通过后，用户分别确认计划与新增 Skill；缺少批准时 Runtime 拒绝启动。

### 12.3 执行

Runtime 锁定计划和 Skill 修订，将 Skill 操作展开到 ExecutionGraph。执行过程只调用已注册执行器；任意未知操作、缺失资源、过期设备租约或未确认参数都进入失败或人工等待状态。

### 12.4 实验上下文沉淀

当前实验保存实际使用的知识引用、Skill 快照、参数、操作回执、人工选择和结果。反馈先形成实验级改进候选，不自动覆盖全局知识或激活新 Skill；发布到全局目录需要独立确认。

## 13. 运行状态与失败语义

```text
DRAFT
  → PLANNING
  → AWAITING_PLAN_APPROVAL
  → APPROVED
  → RUNNING
  ↔ WAITING_OPERATOR
  → VALIDATING_RESULT
  → COMPLETED

执行态可进入 FAILED_SAFE、PAUSED_SAFE、CANCELLED 或 RECOVERY_REQUIRED。
```

- 检索证据不足：计划保留 `unresolved`，禁止启动。
- Agent 引用不存在的事实、Skill、Operation 或 Capability：Validator 拒绝。
- Skill 未批准或修订变化：Runtime 拒绝启动或继续使用已锁定修订。
- 设备离线、超时、拒绝或回执异常：停止推进后继步骤，记录设备状态和停止尝试。
- 人工拒绝：按步骤失败策略进入等待、停止或取消，不自动改写计划。
- 进程中断：首轮投影为 `RECOVERY_REQUIRED`，不自动重发设备命令。
- 结果不满足完成条件：进入结果确认或失败状态，不标记成功。

PDF 与知识线交付版本化 Consumer DTO、能力状态、opaque source/version/citation ID、已发布 SOP 检索结果和独立 Knowledge workspace contributor。Harness 工作区线只保存这些 ID 的项目关联，将选定范围传给 Agent 检索，并挂载 Knowledge contributor；它不读取 Knowledge SQLite、Parser 结果文件或 Embedding 向量。

### 14.3 联合阶段门

1. 接口门：共享 fixture 能表达能力状态、来源版本、引用、确认/冲突、检索模式和已发布 SOP；不兼容时显式失败。
2. 独立门：PDF 线在无 Agent 对话时可以完成录入、审核和召回；Harness 线在 fake Knowledge Consumer 下可以完成项目、多 Session、对话、计划确认和运行卡片。
3. 汇合门：真实 Knowledge contributor 可被 Harness workspace 挂载，项目 source scope 可以约束 Agent 检索，引用能从计划回跳到原始证据。
4. 执行门：Agent 不能批准 Plan、激活 Skill 或推进 Run；对应动作必须由用户触发并由 Approval/Runtime 校验。
5. 完成门：固定 PDF/CSV 与鼠脑实验需求完成“知识发布 → 原生对话规划 → 人工确认 → Mock 执行 → 结果验证 → 报告反馈”，刷新后状态仍可从权威数据恢复。

任何 OpenSpec 任务组预计超过五个工作日，必须继续拆成可独立演示的切片。并行施工以模块所有权和共享 fixture 为约束，不能用复制代码或临时硬编码绕过接口等待。

## 15. 最小原型验收标准

1. 使用未写入产品代码的 PDF、CSV 和鼠脑实验需求完成一次浏览器端到端运行。
2. Knowledge 工作区支持直接选择文件，不要求用户把文件内容复制到文本框；资料导入保留哈希、版本、页码或区块、解析器版本和失败状态。
3. PDF 可以形成带引用的 SOP 草案、缺失项和不可变人工修订；只有审批发布的 SOP 或具名确认事实进入 confirmed planning retrieval。
4. 未配置 Embedding Adapter 时系统明确运行在 FTS5-only 模式；配置后返回关键词/向量混合结果、检索模式、得分和可定位引用，不需要远程向量数据库。
5. Harness 全局侧栏提供 Knowledge、Devices 和 Projects，Knowledge 页面由知识线 contributor 提供，项目页面由 Harness 工作区 contributor 提供。
6. 一个项目可以关联多个 Harness Session；Session 消息与工具事件由 Harness 持久化，项目只保存 source/device/session 的 opaque 引用和共享状态。
7. 用户通过 `ui-conversation` 描述实验需求，Agent 按当前项目范围检索知识、查询设备、补问缺失信息并生成带引用计划，不使用固定 `agentPlan()` 提示按钮作为主流程。
8. Agent 生成的每个计划步骤都有来源、输入输出、完成条件和 Skill 修订；未确认事实、缺失单位、未知操作、未知 Capability、无来源步骤和依赖环均被拒绝。
9. Plan 批准、Skill 校验/批准/激活、Run 启动和步骤确认是分离的人工动作；任何对话指令都不能绕过 Approval 与 Runtime 状态校验。
10. 动态 Skill 草案未经校验和人工批准不能激活；动态脚本不能在首轮自动执行。
11. Runtime 通过 Skill 与 Operation Executor 执行步骤，Agent 不能直接提交设备命令或修改状态。
12. Mock Device 完成健康检查、租约、命令、状态、回执、停止和幂等语义，并至少覆盖一个设备操作、一个人工确认、一个结果验证和一个失败安全停止路径。
13. 运行报告关联用户目标、Session、知识引用、计划、Skill、设备回执、人工选择、结果和反馈。
14. 模型可见事实和用户确认可以从 Session 日志重建，实验缓存丢失不改变审计结果，其他 Session 的未批准内容不会成为当前 Session 的确认上下文。
15. Knowledge 与 Project/Conversation 使用版本化共享 fixture 和独立协议模块；任何一方不可用或版本不兼容时显示明确状态，不伪造成功数据。
16. opt-in composition 在不修改默认 profile 的条件下启动；替换测试资料、Embedding Provider 或 Mock Device 不需要修改 Agent Loop 与 Runtime。

## 16. 测试与完成定义

### 16.1 测试层级

- 领域测试：类型校验、依赖环、单位、来源、Skill 生命周期和状态机。
- Provider 合同测试：知识、Skill、设备和 Runtime 的成功、失败、取消、dispose 与幂等。
- RAG 测试：固定语料的召回、引用准确性、硬过滤、索引删除与重建。
- 双线合同测试：Knowledge capability version、source/version/citation ID、检索结果和 published SOP fixture 在 Provider 与 fake Consumer 间一致。
- 真实组合测试：通过 Loader 启动 opt-in bundle，验证 Provider 与 Consumer 装配。
- Keyless snapshot：覆盖模型可见的检索、计划、拒绝、确认、运行和报告输出。
- Web 测试：真实 Service 路径的资料录入、计划审批、人工确认和失败显示。
- 联合浏览器测试：挂载真实 Knowledge contributor，绑定项目范围，通过 Harness Session 完成召回、计划确认、Mock 执行、验证和报告。

### 16.2 每个增量的完成定义

- 有两分钟内可重复的用户演示。
- 同时覆盖成功路径和一个用户可见失败路径。
- 新增包具有 README、JSDoc、运行 invariant、聚焦测试和真实组合测试。
- 模型或用户可见行为具有 snapshot 或 Web 端到端证据。
- 只运行覆盖当前差异的最小检查，并记录实际命令。
- 非平凡架构或行为决策具有同一变更中的 Agent Note。
- 未完成能力明确显示不可用，不提供静默兜底或虚假成功。

## 18. 风险与控制

| 风险 | 控制 |
| --- | --- |
| Agent 幻觉生成步骤或参数 | 引用必填、结构化输出、Validator、人工批准和未知引用拒绝 |
| 动态 Skill 变成任意代码执行 | 首轮仅声明式生成；脚本候选不自动运行；已安装资源经沙箱和权限执行 |
| RAG 检索结果被当成事实 | 确认状态与来源独立保存；未确认事实不能驱动物理执行 |
| 数据库与 Session 状态分裂 | 知识数据库拥有知识事实；Session 事件拥有模型可见决策与运行时间线；缓存可重建 |
| 模拟结果被误认为真实实验 | 每个回执和报告强制记录 `SIMULATED`、`MANUAL` 或 `PHYSICAL` |
| 首轮范围继续扩张 | 五个增量各自锁定演示目标；真实设备、多运行、自动恢复和动态脚本执行均延期 |
| 设备失败后继续推进 | Runtime 在回执通过和结果校验完成后才提交节点完成事件 |

## 19. 第一轮之后

第一轮闭环通过后，再按证据选择下一方向：增加真实设备 Provider、将动态脚本候选纳入受控构建与审查、增加多实验资源调度、替换远程 RAG Provider、实现跨进程恢复或扩展视觉结果验证。未获得首轮运行证据前不并行建设这些能力。
