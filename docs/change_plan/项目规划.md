# 自动化实验平台项目规划

> 更新时间：2026-08-26

> 文档状态：长期产品与架构参考；当前第一轮施工状态见 [第一轮敏捷开发规划](第一轮敏捷开发规划.md)

> 目标方向：基于 DeepSeek Harness 将当前单 HTML 实验流程演示逐步演进为可审计、可恢复、可接入设备的自动化实验平台

## 1. 文档定位

本文汇总自动化实验平台、演示流程和 DeepSeek Harness 能力的调研结论，用于确定长期产品边界、系统分层、原型路线和后续实现顺序。当前交付范围、OpenSpec 变更和完成条件由 [第一轮敏捷开发规划](第一轮敏捷开发规划.md) 维护，本文不复制实时任务状态。

`competition_health` 项目中的 HTML 文件只用于展示产品流程和交互参考，不是最终页面、业务状态或执行节点的来源。真实后端、数据库、Mock 设备、运行状态和 Web Consumer 按第一轮计划逐步交付；以下前端设计文档继续作为信息架构参考：

- [全流程演示](./Agent实验Workflow全流程整合演示.html)
- [AI Native 实验工作台设计](./superpowers/specs/2026-08-21-ai-native-workspace-design.md)
- [全局能力模块设计](./superpowers/specs/2026-08-21-global-capability-modules-design.md)
- [LabWeave 项目空间架构设计](./superpowers/specs/2026-08-21-labweave-space-project-architecture-design.md)

后端平台的目标不是把 HTML 中的模拟状态直接搬到服务端，而是将其中的业务流程、门禁、人工节点、版本规则和审计要求转换为 dsh 插件能力与持久事件。

## 2. 业务流程调研结论

当前演示围绕 W1-W7 和五个阶段展开，由九个数字员工协作完成：

```text
资料提交与确认
  → 方案生成
  → 实验管理监控
  → 结果收集反馈
  → 实验优化
```

九个角色分别是：

1. 知识库：资料解析、步骤抽取、字段提取、冲突登记。
2. 确认问答：缺口问卷、冲突裁决、时间窗确认、署名记录。
3. SOP 编译：步骤模板化、决策表、设备能力绑定、版本锁定。
4. 实验管理：实验创建、资料预填、样本索引和防串样校验。
5. 调度执行：步骤编排、计时、待办、超时告警和资源锁。
6. 设备接入：设备登记、通信测试、状态同步和人工回报兜底。
7. 视觉判定：图像采集、标准图比对和人工确认。
8. 结果汇总：结果报告、偏差、设备痕迹、时间戳和审签。
9. 反馈优化：偏差证据、版本提案、审批激活和知识沉淀。

### 2.1 资料提交与确认

资料被划分为 F1-F5：

- F1：产品说明书、内部 SOP、历史实验记录和合规文件。
- F2：样本与实验定义、接收标准和异常场景。
- F3：设备台账、通信能力、手册和校准记录。
- F4：人员角色、审批链和责任人。
- F5：视觉标准图、关键手法和隐性经验。

F1、F2 是阻塞项；F3、F4 可以登记为人工回报或线下留痕；F5 可以渐进补齐。资料解析需要保留文件版本、页码、区域位置、字段来源和冲突关系。

### 2.2 方案生成

已确认的资料被编译为机器可执行的实验定义，过程包含：

```text
元模型 → 步骤模板 → 实验实例 → 执行器绑定 → 编排 → 人工确认
```

实验实例必须锁定 SOP、决策表、设备能力和人员规则的版本。新版本不能修改已经开始的实验。

### 2.3 实验执行

步骤至少分为以下类型：

- `machine`：设备自动执行。
- `human`：人工操作并提交完成回报。
- `agent_decision`：Agent 或算法给出建议，必要时等待人工确认。
- `approval`：风险、报废、返工或放行审批。
- `manual_fallback`：设备通信异常后的人工回报。

调度器需要处理时间窗、截止时间、资源锁、并行关系、超时、取消、重试和人工兜底。统一待办应由未完成交互事件投影得到，不应在前端维护一份独立的可变队列。

### 2.4 结果与优化

结果报告需要关联：

- 步骤结果和参数。
- 设备执行痕迹。
- 图像、检测值和样本 ID。
- 偏差、风险和处置。
- 责任人、审批人和时间戳。
- 版本、审签和审计状态。

Agent 只能提出优化方案，不能直接修改并启用 SOP。建议的版本需要具备证据、提出人、审批人、激活时间和回滚信息。

## 3. DeepSeek Harness 的定位

DeepSeek Harness 适合作为实验平台的智能控制平面和人机协作层。根据 [dsh 架构文档](../architecture.md)，dsh 的模型、工具、会话、Agent、工作流、审批和 Web 都通过插件组合，新增实验能力应设计为完整的 Service Definition、Service Provider 和 Consumer，而不是修改 Agent Loop。

建议的职责划分如下：

### 3.1 dsh 控制平面

- Agent 角色和委派。
- 文档、知识和实验定义的对话式处理。
- 人工问题、审批、签名和确认。
- 实验创建、启动和状态查询工具。
- Session 事件、审计和模型上下文。
- Web 页面、卡片和统一待办投影。
- 报告、变更提案和版本说明。

### 3.2 实验执行平面

- 设备命令和设备状态。
- 长时间计时和后台执行。
- 资源锁和设备占用。
- 图像采集、检测和测量。
- 文件及实验结果存储。
- Worker 崩溃后的恢复、重试和幂等。

设备和执行服务必须通过 dsh 的能力接缝接入，Agent 不能直接获得设备驱动、数据库或文件系统的无限制权限。

## 4. dsh 能力映射

| 业务能力 | 复用的 dsh 能力 | 新增内容 |
|---|---|---|
| 资料上传 | `ctx.fs`、Web 上传和 Session | 实验资料服务、文档解析 Provider |
| 冲突问答 | `ctx.userQuestions` | 冲突卡片、问题类型和裁决事件 |
| 风险审批 | `ctx.approval` | 实验风险、返工、报废和放行的审批 Consumer |
| Agent 协作 | `ctx.agents`、`ctx.subagents`、Skill | 九个业务角色的 Preset、工具范围和移交规则 |
| 短流程编排 | `ctx.workflowEngine` | 实验定义编译器，不把模型脚本作为唯一事实来源 |
| 后台工作 | `ctx.jobs` | 实验运行 Provider、持久化任务或外部 Worker |
| 会话与审计 | `ctx.sessions`、SessionEventMap、持久化 | 实验领域事件、投影和查询索引 |
| Web 展示 | dsh Web、会话事件、ConversationNodeDefinition | 冲突、人工步骤、视觉判定、审批和审签卡片 |
| 文件和结果 | `ctx.fs`、Artifact Provider | 文件哈希、来源、样本关联和生命周期 |
| 设备操作 | `ctx.subprocess`、`ctx.shell`、`ctx.sandbox` | DeviceRegistry、DeviceExecutor 和外部设备适配器 |
| 运行遥测 | dsh 的 Session Telemetry OTEL 能力 | 设备、Agent、步骤和请求的关联 trace |

需要特别注意：当前 dsh workflow 主要是前台收集，且没有工作流检查点和恢复能力；当前本地 jobs Provider 只保存进程内任务。因此它们可以支持第一版模拟演示，但不能直接满足跨天实验和进程重启恢复。

## 5. 建议新增的核心能力接缝

第一版不建议按九个数字员工新增九个独立运行时插件，而是先建立四个业务能力接缝。

### 5.1 ExperimentDefinitionService

负责 SOP、步骤、决策表、资源需求、设备能力和人工交互要求的编译与校验。

核心对象建议包括：

```text
ExperimentDefinition
├── id / version / source
├── steps[]
├── decisionTables[]
├── deviceRequirements[]
├── humanInteractionRequirements[]
└── provenance[]
```

### 5.2 ExperimentRunService

负责实验实例和执行运行：

- 创建、启动、暂停、恢复和取消。
- 步骤状态、尝试次数和执行游标。
- 时间窗、截止时间和超时。
- 资源锁、依赖关系和并行关系。
- 人工等待、审批门和手工回报。
- 运行版本固定、失败和重规划。

### 5.3 DeviceRegistry / DeviceExecutor

负责设备注册、能力描述、状态、占用和命令执行。执行接口必须定义超时、取消、幂等键、完成码、通信失败和人工兜底。

建议先提供 `SimulatedDeviceProvider`，用固定的模拟设备完成端到端流程；真实设备 Provider 后续按设备类型独立接入。

### 5.4 KnowledgeService

知识服务分为两层：

- 结构化事实：样本标准、时间窗、设备能力、审批规则、版本和责任人。
- 语义检索：文档片段、历史经验、图像说明和 SOP 相关内容。

向量库只用于检索，不能替代结构化事实和来源审计。每条知识应带来源文件、版本、页码或区域、解析时间、裁决人和当前有效版本。

## 6. 建议的数据和事件模型

### 6.1 领域对象

```text
ExperimentDefinition   实验定义和 SOP 版本
ExperimentInstance     一次具体实验、样本和快照
ExecutionRun           一次执行运行和当前状态
StepExecution          步骤尝试、输入、输出和错误
InteractionRequest     人工问题、审批、视觉确认或手工回报
ResultArtifact         文件、图像、检测值和设备日志
ChangeProposal         SOP 或参数变更提案
Revision               已审批、已激活或已回滚的版本
```

领域 ID 使用不透明、带品牌的 ID，避免用普通字符串在不同资源之间混淆。大文件和图像不直接塞进会话事件，事件保存 artifact ID、哈希、来源和关联关系。

### 6.2 最小事件集合

```text
experiment/created
experiment/definition-locked
experiment/started
experiment/step-started
experiment/step-waiting-human
experiment/step-completed
experiment/step-failed
experiment/resource-locked
experiment/approval-requested
experiment/approval-decided
experiment/artifact-added
experiment/report-generated
experiment/signed
experiment/change-proposed
experiment/change-approved
experiment/revision-activated
experiment/cancelled
```

事件日志记录控制平面事实和模型可见输入；结构化数据库或投影用于列表、筛选、报表和设备查询。不能让前端状态成为实验状态的唯一来源。

## 7. 九个数字员工的实现方式

| 角色 | 第一版实现 | 必须由服务强制的规则 |
|---|---|---|
| 知识库 | Agent + 文档解析工具 | 原文来源和冲突不能丢失 |
| 确认问答 | `userQuestions` Consumer | 裁决必须署名并写入事件 |
| SOP 编译 | Agent + Definition Compiler | 编译失败不能生成可执行版本 |
| 实验管理 | Tool / Command | 样本索引唯一、实验快照锁定 |
| 调度执行 | 确定性 Run Service | 时间窗、资源锁和超时不能由模型决定 |
| 设备接入 | Device Provider | 命令权限、超时、完成码和人工兜底 |
| 视觉判定 | 算法工具 + 人工确认 | Agent 只能建议，不能绕过 QC |
| 结果汇总 | Projection + Report Consumer | 报告必须关联证据和版本 |
| 反馈优化 | Change Proposal Agent | 变更必须审批后激活，旧实验不受影响 |

九个角色不建议全部常驻。知识库、SOP、报告和优化可以按需由 Agent Preset 启动；调度、设备、资源锁和超时处理应当是确定性服务。

## 8. 第三方开源组件选择

下列项目不是现成的 dsh 插件，需要包装成 dsh Provider 或 Consumer。

### 8.1 文档解析：Docling

[Docling](https://github.com/docling-project/docling) 适合用于 PDF、DOCX、PPTX、XLSX、HTML 和图像资料的结构化解析、表格提取、版面信息和页码溯源。建议以本地进程或独立服务方式运行，由 dsh 文档 Provider 调用。

第一版只需要把解析结果规范化为步骤、字段、来源和冲突候选，不要让模型直接把原始文档当作事实来源。

### 8.2 结构化数据和语义检索：PostgreSQL + pgvector

[pgvector](https://github.com/pgvector/pgvector) 可在 PostgreSQL 中提供向量相似度检索。推荐将实验、版本、设备、人员、审批和来源信息保存为普通关系表，将向量检索作为知识召回能力。

如果原型需要尽快单机运行，可以先复用 dsh 的 SQLite/JSONL 持久化和本地文件；知识规模增加后再迁移到 PostgreSQL + pgvector。

[Qdrant](https://qdrant.tech/documentation/) 可以作为独立向量检索服务的备选，但第一版不建议同时引入 PostgreSQL、Qdrant 和其他检索系统。

### 8.3 实验设备：PyLabRobot 或 SiLA 2

[PyLabRobot](https://github.com/PyLabRobot/pylabrobot) 适合液体处理和部分实验室设备控制；[SiLA 2](https://sila2.gitlab.io/sila_base/) 更适合以标准协议连接不同厂商的实验设备。

选择原则：

- 设备已有 SiLA 2 支持时，优先做 SiLA Provider。
- 设备属于 PyLabRobot 已覆盖的实验室设备时，做 PyLabRobot Bridge。
- 设备只有厂商 SDK 或 HTTP/MQTT 接口时，先做单设备适配器，不要为了统一而强行引入复杂标准。
- 在真实设备未确定前，统一使用模拟设备 Provider。

### 8.4 可观测性：OpenTelemetry

[OpenTelemetry](https://opentelemetry.io/docs/) 适合记录 Agent 请求、实验运行、步骤执行、设备通信和人工等待之间的 trace 关系。dsh 已有 Session Telemetry OTEL 方向，后续应优先做关联 ID 和 span 对齐，而不是另起一套日志体系。

### 8.5 长时间可恢复编排：Temporal

[Temporal](https://docs.temporal.io/) 适合跨进程、跨主机、长时间等待和失败恢复。它不建议作为第一版依赖；当实验运行需要跨天恢复、多 Worker 和复杂定时器时，再将 Temporal 封装为 `ExperimentRunService Provider`。

不建议第一版同时引入 LangGraph、CrewAI、Temporal 等第二套 Agent 或工作流编排框架。dsh 已有 Agent、subagent、workflow 和 jobs 接缝，外部框架应作为局部 Provider，而不是成为第二个全局控制平面。

## 9. 推荐的原型路线

### 9.1 原型目标

使用一条可控的模拟实验流程验证：

1. F1-F5 资料提交和阻塞项检查。
2. 文档解析结果、来源和冲突登记。
3. 两个确认问题和一个署名裁决。
4. SOP 编译为 8-12 个步骤。
5. 模拟设备执行和资源占用。
6. 一个人工操作节点。
7. 一个视觉判定节点。
8. 一个 QC 风险审批节点。
9. 报告生成、审签和审计闭合。
10. 生成 SOP 变更提案，但不自动启用。

### 9.2 原型技术组合

```text
dsh Web Profile
  + Experiment Definition Service
  + Experiment Run Service
  + Simulated Device Provider
  + dsh userQuestions / approval
  + Session EventMap + SQLite/JSONL
  + Docling Adapter
  + 本地 artifact 文件目录
```

第一版不接入真实设备、不声明实验结果具有生物学有效性，也不把模拟成功率作为实际业务指标。

### 9.3 建议的包边界

以下名称为拟议名称，实施前需要结合 dsh 现有包分组和组合规范确认：

```text
@deepseek-ai/dsh-experiment
    实验定义、实验运行和领域类型的 Service Definition

@deepseek-ai/dsh-experiment-local
    本地实验 Provider、事件投影和模拟运行

@deepseek-ai/dsh-tool-experiment
    面向 Agent 的实验创建、查询、确认和报告工具

@deepseek-ai/dsh-experiment-simulated-device
    模拟设备注册、能力和执行 Provider

@deepseek-ai/dsh-experiment-docling
    Docling 进程或服务的文档解析 Provider

@deepseek-ai/dsh-experiment-web
    冲突、人工步骤、视觉判定、审批和审签的 Web 展示 Consumer
```

这些包应遵循 dsh 的 capability seam 结构，先完成 Service Definition，再分别实现 Provider 和 Consumer；不要先把业务逻辑全部写进 Web 页面。

## 10. 分阶段实施计划

### 阶段 0：规划和边界确认

- 确认第一条实验流程和样本类型。
- 确认第一批设备及其通信方式。
- 确认 F1-F5 的实际文件样例。
- 确认哪些节点必须人工审批。
- 确认原型只做模拟设备还是需要一个真实设备联调。

### 阶段 1：dsh 原生模拟闭环

- 建立 Experiment Definition 和 Experiment Run 接缝。
- 建立实验事件和最小投影。
- 接入 `userQuestions`、`approval` 和 Web 卡片。
- 用模拟设备跑通一条 8-12 步流程。
- 验证启动、暂停、人工等待、审批、完成和失败状态。

### 阶段 2：资料解析和知识沉淀

- 接入 Docling。
- 保留文件、页码、区域和字段来源。
- 将冲突、时间窗和缺口转换为可确认问题。
- 增加结构化知识表和来源查询。
- 再评估是否需要 pgvector。

### 阶段 3：真实设备适配

- 建立设备注册和能力模型。
- 先接一个设备，不同时接入全部设备。
- 支持通信失败、完成码、人工回报、取消和幂等。
- 将设备执行结果写入实验事件和 artifact 关联。

### 阶段 4：长时间运行和生产化

- 增加持久化 Run Provider 和 Worker。
- 增加跨进程恢复、资源锁续租和任务重试。
- 接入 OpenTelemetry trace。
- 根据运行时长和设备规模决定是否引入 Temporal。
- 增加多用户、角色、租户和数据保留策略。

## 11. 关键风险和控制规则

### 11.1 Agent 越权

Agent 只能通过工具和服务操作实验；设备命令、版本激活、风险放行和报告签名必须由服务和审批层强制控制。

### 11.2 状态分裂

Session 事件是模型可见控制事实的记录来源；数据库和前端只保存查询投影或索引。不得让 HTML 状态、Agent 内存或独立任务队列成为唯一事实来源。

### 11.3 版本污染

实验开始时锁定定义、设备能力、知识和人员规则的版本。后续优化生成新版本，不修改进行中的实验。

### 11.4 设备不可靠

每个设备执行都需要明确超时、取消、完成码、重试规则和人工兜底。通信中断时必须显示人工兜底状态，不能显示为自动执行成功。

### 11.5 视觉和实验结论风险

视觉模型或 Agent 可以产生建议和风险标记，但实验放行、返工、报废和生物学结论必须经过配置的规则、算法验证或人工签名。

## 12. 验收标准

第一版原型达到以下条件后，才进入真实设备适配：

- 从资料提交到报告审签可以完整执行一次。
- F1、F2 缺失时无法进入解析和方案生成。
- 文档冲突可以被提出、回答、署名并写入事件。
- 实验实例能锁定 SOP 版本，运行中不会被新版本覆盖。
- 模拟设备执行、人工步骤、视觉判定和 QC 审批在同一条运行记录中可追踪。
- 设备或任务失败时能进入人工兜底或失败状态，不能静默成功。
- 报告可以关联步骤结果、artifact、设备日志、审签和版本。
- 反馈只能生成变更提案，不能无审批激活。
- dsh Web 重载后，至少可以从持久 Session 恢复实验控制平面状态。
- 原有单 HTML Demo 的信息架构仍可作为前端验证参考，但不再作为后端状态来源。

## 13. 当前需要确认的事项

以下内容在进入代码实现前需要确认，本文暂不擅自决定：

1. 第一条真实目标实验是空间转录组、空间 ATAC、SeekOne DD，还是其他流程。
2. 第一批设备的型号、通信协议和是否允许模拟器先行。
3. F1-F5 实际资料是否包含敏感样本、个人信息或合规限制。
4. 原型阶段使用 SQLite/JSONL，还是直接部署 PostgreSQL。
5. 视觉判定第一版是人工确认、规则判定，还是接入已有模型。
6. 是否需要在第一版实现跨进程或跨天恢复。

在这些事项确认前，建议只实现模拟设备和控制平面，不连接真实设备、不发布自动优化版本。
