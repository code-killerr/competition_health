# AI Native 实验工作台三阶段修复设计

## 目标

在保留现有对话式规划体验的前提下，把页面从“静态演示状态”收敛为可解释的实验工作台：每个实验项目拥有独立状态，规划与执行有明确门禁，执行结果可以通过/失败并驱动重规划，全局设备能力可以被项目引用。

## 参考结构

- 项目总览参考控制台：顶部当前项目上下文、关键指标、最近实验表格和快捷入口。
- 项目列表参考实验管理：搜索、状态筛选、进度/证据链、详情与切换项目。
- 设备管理参考设备库：设备总览指标、搜索/类型/状态筛选、设备能力字段和能力模型。

参考页面只吸收信息架构和业务字段，不复制外部站点的品牌、文案或视觉资产。

## 三阶段范围

### 阶段一：项目域与阶段门禁

新增项目级上下文模型：规划步骤、知识状态、Workflow 版本、资源计划、执行游标、结果状态和归档状态均按项目保存。全局能力（知识库、Agent、Workflow 模板、设备、人员）继续独立维护，通过 ID 和版本被项目引用。

项目页面的进入规则：

```text
planning → confirm（planComplete）
confirm → execution（计划已锁定）
execution → archive（resultStatus=passed）
execution → orchestration（异常或人工编排）
```

侧栏可以展示模块，但不能绕过门禁直接改变项目阶段。项目总览和项目列表都必须通过同一个 `selectProject(id)` 更新当前项目。

### 阶段二：执行闭环与资源编排

Workflow 定义作为唯一来源，执行事件通过 Workflow ID 生成，避免确认页、执行页和归档页维护三套步骤。每个执行节点包含状态、结果、风险、资源和失败策略。

执行状态必须支持：

```text
queued → running → awaiting_result → passed
                                  ↘ failed → replanning → awaiting_confirmation
```

Agent 重规划必须生成新版本和差异摘要，并同步执行队列、资源预约与归档记录。手动编排需要校验依赖关系，至少阻止把步骤排到其前置步骤之前。

### 阶段三：全局能力工作台

设备页按参考设备库补充：设备统计、搜索、类型筛选、状态筛选、设备列表、能力字段、连接方式、当前占用和能力模型。设备状态拆分为通信状态、启用状态和人工兜底模式，不能把人工兜底显示成自动连接成功。

知识库、Agent、Workflow、设备和人员配置均保存全局状态；项目只保存引用关系和锁定版本。配置页的保存动作应更新状态，并在项目页面显示引用版本或缺口。

## 关键交互

1. 从项目列表选择项目后，项目总览、规划、执行和归档都保持同一项目上下文。
2. 规划中发现缺口时，跳转到对应全局能力页；完成后回到原项目并恢复规划游标。
3. 进入执行前显示最终计划、资源冲突和版本；确认后锁定计划。
4. 执行中出现异常时，用户可以让 Agent 重规划或进入步骤编排；两者都要回写执行计划。
5. 结果判断必须显式展示通过/失败；失败时生成重规划入口，通过后才允许归档。

## 非目标

- 不接入真实设备、真实实验数据或后端 API。
- 不重写为 React/Vue，继续保持单 HTML 交付，便于当前演示打开和分享。
- 不复制外部参考页面的品牌视觉。

## 验收标准

- 切换项目后，规划、知识引用、Workflow、执行进度和归档内容不串项目。
- 未完成规划时不能进入确认、执行或归档。
- 8 个 Workflow 在确认页、执行页和归档页一致，执行事件不跳步。
- 异常重规划会改变后续执行队列，并在版本差异中可见。
- 设备中断并切换人工兜底时，不再显示“设备已通过测试并启用”。
- 设备页具备参考页面中的统计、筛选、列表和能力模型信息。
- JS 可解析、无重复 ID，关键入口可通过静态检查和浏览器回放验证。
